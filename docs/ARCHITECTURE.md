# КАИ Расписание — как устроено

Техническая документация. Обзор проекта — в [README](../README.md).

Студент открывает сайт, выбирает группу и видит расписание. Преподаватель по фамилии находит свои часы. Специалист учебной части ведёт и расписание, и план нагрузки в одной админке.

Этот документ — карта проекта: его цель не только объяснить, как запустить, но и передать контекст другому разработчику (или другой нейросети) без чтения всего кода. Правила для ИИ-ассистентов лежат отдельно в `CLAUDE.md`.

**Стек:** React 19 + Vite, Express 5, SQLite (better-sqlite3). Один процесс, одна база-файл.

---

## 1. Роли

| Кто | Что делает | Вход |
|---|---|---|
| Студент | Смотрит расписание своей группы и подгруппы, листает даты, работает офлайн через PWA | не нужен |
| Преподаватель | Ищет себя по фамилии, видит план и сколько часов уже проведено, с разбивкой по датам | не нужен |
| Специалист | Ведёт расписание, план нагрузки, семестры, справочники, выгрузки, бэкапы | логин и пароль |

Записывать данные может только специалист. Всё остальное — чтение.

## 2. Запуск

```bash
npm install
cp .env.example .env          # заполнить JWT_SECRET

npm run dev                   # Vite :5173 + Express :3000 вместе
npm run dev:client            # только фронт, /api проксируется на :3000
npm run dev:server            # только сервер, с --watch

npm run build                 # сборка фронта в dist/
npm start                     # Express отдаёт dist/ и /api
npm run start:build           # собрать и запустить

npm test                      # все тесты (node --test)
npm run seed                  # ОПАСНО: пересоздаёт базу с демо-данными
```

База создаётся сама при первом запуске. Если рядом лежит снимок `seed/schedule.seed.db`, пустая база разворачивается из него. В репозитории снимка нет: реальные данные (преподаватели, учётка администратора) в git не хранятся.

## 4. Как устроено

```
Браузер ──► Vite (dev) / Express (prod) ──► SQLite (файл на диске)
   │
   └── Service Worker: кэш оболочки и последних данных расписания
```

**Плохая сеть.** В вузе сеть чаще не падает, а «висит»: запрос не обрывается 10–20 секунд. Поэтому Service Worker ждёт сеть ограниченное время (страница 2 с, стили 1,5 с, расписание 2,5 с), а дальше отдаёт сохранённую копию и дописывает свежий ответ в кэш, когда тот придёт. Сохранённая копия помечена заголовками `X-Kai-Saved-Copy` и `X-Kai-Saved-At`: страница показывает, от какого времени расписание, и каждые 5 секунд пробует обновиться, пока сервер не ответит. Кэш данных не привязан к версии приложения, поэтому обновление сайта не стирает сохранённое у студентов.

В проде Express отдаёт собранный `dist/` и обслуживает `/api`. Никаких внешних сервисов, очередей и второй базы нет.

## 5. Доменная модель

Это главная часть проекта. Всё остальное — обвязка.

### 5.1 Семестр

Каждое занятие принадлежит семестру (`lessons.semester_id`). Номера недель, чётность и часы считаются **внутри своего семестра** — поэтому весну можно строить в январе, не трогая осенние цифры.

«Какой сейчас семестр» — это три разных вопроса, и их нельзя смешивать:

| Вопрос | Кто спрашивает | Ответ в коде |
|---|---|---|
| В каком я работаю | Конструктор, загрузка из Excel | `getActiveSemester` — помеченный `is_active`, ровно один |
| Какой идёт по календарю | Студент, преподаватель | `getSemesterForDate` — по дате |
| Какой я открыл посмотреть | Специалист в разделе нагрузки | локальное состояние страницы, на сервере не хранится |

Семестры не пересекаются: новый начинается только после последней учебной недели другого, иначе ошибочная дата перехватила бы чужие недели у студентов. Дата начала меняется только в разделе «Нагрузка» с предпросмотром последствий (в Настройках её нет). Пару после последней недели поставить нельзя: конструктор предлагает сначала продлить семестр, чтобы пара и показывалась, и засчитывалась.

Дата начала семестра всегда приводится к понедельнику своей недели: если ввести вторник, недели пошли бы со вторника по понедельник и понедельничные пары уехали бы в чужую неделю.

### 5.2 Чётность недели

У семестра хранится чётность **первой** недели (`first_week_parity`: 1 — нечётная, 2 — чётная), дальше строгое чередование. Календарная чётность (по номеру ISO-недели) используется только как значение по умолчанию при создании семестра.

Так сделано намеренно: в 2026 году 53 ISO-недели, поэтому «по календарю» и «чередуя от сентября» совпадают всю осень и расходятся всю весну. Какой вариант у кафедры — это факт из документа, а не то, что можно вывести.

### 5.3 Шаблон и недели

У занятия есть поле `specific_week`:

- `NULL` — **шаблонная** запись, действует во все недели подходящей чётности (`week_type`: 0 — каждую, 1 — нечётные, 2 — чётные);
- число `N` — запись **конкретной недели** N.

Правило: **если у недели есть свои записи, шаблон для неё игнорируется целиком.** Никакого смешивания. Так работает и настоящая кафедра: вывешенное на неделю расписание главнее шаблона.

Отсюда следствие: убрать из недели последнюю пару нельзя просто удалением — иначе у недели не осталось бы своих записей и вернулся бы шаблон. Поэтому отмена оставляет запись-отметку с `is_removed = 1`: она не показывается и не считается, но неделя остаётся «своей».

### 5.4 Версии: правка не переписывает прошлое

Шаблонные записи версионируются полем `template_from_week`. Правка пары не меняет старую строку, а добавляет новую с пометкой «действует с текущей недели». Удаление добавляет надгробие с той же пометкой.

`resolveTemplateLessons` для недели N берёт по каждой ячейке версию с наибольшим `template_from_week ≤ N` и отбрасывает надгробия.

Поэтому: убрали пару в ноябре — октябрьские недели остаются как были, и часы за них у преподавателя сохраняются. Если пара этой ячейки на текущей неделе уже прошла (в среду правят понедельник), изменение начинается со следующей недели: прошедшая пара и её часы остаются (`utils/templateWeek.js`). Номер недели для новой версии сервер берёт **только из своих часов**, никогда из запроса — иначе клиент мог бы задним числом переписать, что показывала прошлая неделя.

Важно: новая версия наследует `teacher_id`/`discipline_id` у той, которую заменяет. Иначе студенты видели бы новую пару, а часы продолжали бы считаться по старой (см. 5.5 — совпадение автоматическое, по этим полям).

### 5.5 Часы

Часы **нигде не хранятся** — они выводятся из расписания. Источник истины один, расходиться нечему.

Строка плана и пара в расписании — это одно и то же преподавание, если у них совпадает **вся** пятёрка: `teacher_id`, `discipline_id`, `lesson_type`, `group_id`, `subgroup` (в пределах одного семестра). Специалист ничего отдельно не привязывает: она выбирает преподавателя и предмет из тех же самых справочников (`teachers`/`disciplines`), что и в конструкторе, — и как только пара с такой пятёркой появляется в расписании, часы по ней считаются сами. Задним числом переправили неделю с английского на русский — старому преподавателю часы автоматически упадут, новому вырастут, без единого лишнего клика.

```
строка плана (teacher_id + discipline_id + lesson_type + group_id + subgroup, план в часах)
        │
        │  совпадение автоматическое: та же пятёрка на паре в расписании
        ▼
идём по неделям 1..weeks_count: что действовало на этой неделе?
если пара закончилась раньше «сейчас» — плюс 2 академических часа
```

2 академических часа за пару — это 2 × 45 минут, сверено с планами кафедры (32 плановых часа = 16 пар).

Одна строка плана может владеть несколькими парами в неделю (лекция в две пары подряд, практика в понедельник и в среду) — считаются все.

Текст (`lessons.subject`/`lessons.teacher`) остаётся на каждой паре — для отображения, выгрузок и разовых замен без своей карточки в справочнике, — но как только у пары указан `teacher_id`/`discipline_id`, сервер всегда подставляет текст из справочника сам (`resolveTeacherDiscipline` в `admin/shared.js`), не доверяя тексту, присланному клиентом рядом с id. Это и не даёт тексту с id разойтись. Пара без выбора из списка (разовая замена, гость) показывается студентам как обычно, но в часы не идёт — это ожидаемо, а не баг: для того же преподавателя на постоянной основе достаточно завести его в справочнике один раз.

Совпадение строгое: хватит одного неверного поля (тип, подгруппа) или вписанного руками преподавателя, чтобы пара перестала считаться, и обычно это происходит молча. Поэтому `GET /api/admin/load-plan/unmatched` возвращает пары, которые расписание показывает, но ни одна строка плана не забирает, а раздел нагрузки показывает их списком. Учитывается только то, что действует сейчас: снятые версии шаблона, удалённые пары и мероприятия (`kind = event`) в список не попадают.

Удалить преподавателя или дисциплину из справочника нельзя, пока на них ссылается хоть одно занятие (`lessons.teacher_id`/`discipline_id`) любого семестра — не только строка плана. Переименование в справочнике не трогает историю: пары продолжают ссылаться на тот же `id`.

Единственное место, где часы берутся из базы, — `utils/planProgress.js`. Его используют страница преподавателя, список плана в админке, выгрузка в Excel и предпросмотр последствий.

### 5.6 Закрытие семестра

`POST /api/admin/semesters/:id/close` фиксирует итог: часы каждой строки плана записываются в `load_plan.final_hours`, семестр получает `closed_at`.

После этого:

- любая запись внутрь этого семестра отклоняется с кодом 409 (пары, загрузка, строки плана, даты семестра);
- часы отдаются из сохранённого снимка, а не пересчитываются — значит цифра в подписанном отчёте не изменится, даже если время идёт дальше;
- `POST .../reopen` возвращает живой пересчёт.

### 5.7 Потоки и объединённые группы

Одна лекция для нескольких групп сразу — **одна** строка плана: первая группа в `load_plan.group_id`, остальные в `load_plan_extra_groups` (`utils/planGroups.js`). Пары по группам сводятся по дате и времени, поэтому общая пара считается один раз — 2 часа, а не 2 на каждую группу.

Группа, которая учится вместе с другой (23313 с 23303), объединяется с ней в настройках: своих пар у неё нет, студенты видят пары ведущей группы под своим номером (`utils/groupJoin.js`).

### 5.8 Неподтверждённые недели

Прошедшая неделя без своих записей — это либо «всё шло по шаблону», либо «про неё забыли». Система их не различает, поэтому просто называет: `GET /api/admin/semesters/:id/week-coverage` возвращает список таких недель, раздел нагрузки показывает предупреждение, а окно закрытия семестра повторяет его и пишет список в журнал.

### 5.9 Сессия: экзамены, зачёты, консультации

Хранятся в отдельной таблице `attestations`, не в `lessons`: у них настоящая дата и свободное время начала (конец необязателен), чаще всего они идут после последней учебной недели. Запись с `specific_week` в `lessons` сделала бы эту неделю «своей» и стёрла бы шаблон, поэтому в общую таблицу их не кладут. Семестр записи — тот, что действует на её дату.

- **В часы не идут.** В разделе «Сессия» считается только количество у каждого преподавателя.
- **Студенты** видят их в своём дне рядом с парами, с оранжевой меткой вида (`scheduleResolve.js`). **Преподаватель** видит блок «Сессия» на своей странице.
- **Вводятся в приложении**, а наружу выгружаются двумя кнопками в формате филиала: «Расписание промежуточной аттестации» (даты в колонках «зачет» и «экзамен») и «Расписание консультаций к экзаменам» (`server/exportAttestations.js`). Импорта из Excel нет: от него отказались, источник данных — приложение.
- **Пересечения** (`utils/attestationConflicts.js`). Отказ — только для точного повтора записи. Остальное — предупреждение, которое специалист подтверждает: пара у группы в это время (дни разбираются так же, как на странице студента), занятые преподаватель или аудитория, консультация после последнего экзамена, воскресенье. Совместный экзамен двух групп в одно время — не конфликт. Список перепроверяется при каждом открытии, поэтому пара, добавленная позже в конструкторе, отмечается значком ⚠ у записи.

## 6. API

### Публичное (без авторизации)

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/health` | Состояние процесса и базы; вне лимита запросов, для внешнего монитора |
| GET | `/api/universities` | Список вузов |
| GET | `/api/universities/:id/groups` | Группы вуза |
| GET | `/api/schedule/:groupId` | Расписание группы: `?date=&span=semester` — весь семестр, в который попадает дата (страница грузит так); или `?date=&days=` (до 400); `&subgroup=`. Заголовок `X-Kai-Range` — какие дни в ответе |
| GET | `/api/semesters` | Семестры с пометкой, закрыт ли |
| GET | `/api/teachers/search?q=` | Поиск преподавателя по части фамилии |
| GET | `/api/teachers/:id/load` | План и часы преподавателя, плюс `attestations` (его экзамены, зачёты, консультации); по умолчанию — семестр по дате, иначе `?semester_id=` |
| POST | `/api/alice` | Навык Алисы (Яндекс Диалоги): отвечает расписанием группы, группу помнит хранилище навыка |
| POST | `/api/client-error` | Сообщение об ошибке интерфейса (шлёт `ErrorBoundary`) |

`/api/schedule/:groupId` возвращает и список семестров, попавших в диапазон, и все занятия с их `semester_id`. Решение «что показать в конкретный день» принимает клиент — `src/lib/scheduleResolve.js`.

### Админское (`/api/admin`, JWT в httpOnly-cookie + CSRF)

Группы: `GET|POST /groups`, `PUT|DELETE /groups/:id` (удаление запрещено, пока в группе есть занятия).

Расписание: `POST /schedule/upload`, `POST /schedule/upload-bulk`, `GET /schedule/export`, `POST /schedule/move-lesson`, `POST /schedule/materialize-week`, `DELETE /schedule/week`.

Занятия: `GET|POST /lessons`, `PUT|DELETE /lessons/:id` (`teacher_id`/`discipline_id` — из справочника, для автоматического совпадения с планом).

Нагрузка: `GET|POST /load-plan`, `PUT|DELETE /load-plan/:id`, `GET /load-plan/export`, `GET /load-plan/unmatched` (пары, часы по которым не идут ни в одну строку плана).

Справочники: `GET|POST /teachers`, `PUT|DELETE /teachers/:id`, то же для `/disciplines` (удаление запрещено, пока есть строка плана или хоть одно занятие, ссылающееся на запись).

Сессия: `GET|POST /attestations`, `PUT|DELETE /attestations/:id` (при пересечениях — 409 с `needs_confirm` и списком `warnings`, повтор с `confirm: true`), `GET /attestations/export?type=session|consultations`.

Семестры: `GET|POST /semesters`, `PUT /semesters/:id`, `POST /semesters/:id/close`, `POST /semesters/:id/reopen`, `GET /semesters/:id/impact` (предпросмотр: как изменение дат повлияет на часы), `GET /semesters/:id/week-coverage`.

Служебное: `POST /login`, `POST /login/second-factor` (код из приложения или резервный код после пароля), `POST /logout`, `GET /session`, `PUT /account`, `GET /account/security`, `POST /account/totp/setup|enable|disable|recovery-codes`, `POST /account/logout-everywhere`, `GET|PUT /settings`, `GET /audit-logs`, `GET /audit-logs/export`, `GET|POST /backups`, `GET /backups/:file/download`, `POST /backups/:file/restore`, `POST /backups/upload-restore`.

## 7. Схема базы

| Таблица | Ключевое |
|---|---|
| `universities`, `groups_` | Иерархия вуз → группа |
| `semesters` | `start_date` (всегда понедельник), `weeks_count`, `first_week_parity`, `is_active` (не более одного), `closed_at` |
| `lessons` | Ядро: `semester_id`, `group_id`, `subgroup`, `day_of_week`, `week_type`, `specific_week`, `template_from_week`, `is_removed`, время, `subject`/`teacher` (текст), `teacher_id`/`discipline_id` (nullable, из справочников — по ним автоматически совпадает с планом), `kind` (`lesson` или `event`) |
| `teachers`, `disciplines` | Справочники |
| `load_plan` | Строка плана: семестр, преподаватель, дисциплина, тип, группа, подгруппа, `planned_hours`, `final_hours` (заполняется при закрытии) |
| `attestations` | Экзамены, зачёты, консультации: `kind`, `date`, `time_start`/`time_end`, группа, подгруппа, `semester_id`, `discipline_id`/`teacher_id` или текст, если в справочнике нет |
| `settings` | Ключ-значение; `semester_start_date` дублирует дату рабочего семестра |
| `admins`, `audit_logs`, `login_attempts` | Вход, журнал действий, защита от подбора |

`kind = 'event'` — линейка, субботник и подобное: занимает ячейку, показывается, но никому не идёт в часы.

Миграции выполняются при старте в `db.js`, все безопасны для повторного запуска. Перед ними автоматически снимается копия базы.

Таблицы `date_overrides` и `date_lessons` остались от более ранней модели, кодом не используются и пусты.

## 8. Массовая загрузка расписания

`POST /api/admin/schedule/upload-bulk` — всё или ничего:

```json
{
  "target_week": "template",
  "groups": [
    {
      "group": "23113",
      "university": "КНИТУ-КАИ",
      "lessons": [
        {
          "day": 1,
          "time_start": "08:00",
          "time_end": "09:30",
          "subject": "Программирование",
          "room": "305",
          "type": "Лекция",
          "teacher": "Иванов И.И.",
          "week_type": "all",
          "subgroup": 0
        }
      ]
    }
  ]
}
```

`target_week`: `"template"` — в шаблон, `"current"` — в текущую неделю, число — в конкретную. `week_type`: `all`, `odd`, `even`.

Загрузка идёт в **рабочий** семестр и отклоняется, если заменяемые записи уже совпадают со строкой плана (есть `teacher_id`+`discipline_id`): иначе преподаватель молча потерял бы уже посчитанные часы.

## 9. Бэкапы и восстановление

- **При каждом старте** сервера, до миграций, снимается копия. Если обновление сломает структуру базы, состояние «до» лежит на диске.
- **Раз в сутки** — ещё одна. Хранится 5 стартовых и 14 суточных; если места на диске мало, копия пропускается с записью в лог.
- **Вручную** — кнопка в админке.
- **Восстановление** — в панели: из списка или из скачанного ранее файла. Файл сначала проверяется (целостность SQLite, нужные таблицы, хотя бы один администратор), текущее состояние сохраняется отдельной копией, и если восстановленный файл не открылся — возвращается прежний. Копия старой схемы при восстановлении мигрирует сама.

Эти копии лежат рядом с базой и защищают от плохой записи и неудачной миграции. От потери самого сервера защищает внешняя копия: каждые 6 часов зашифрованный архив базы уходит на облачный диск.

## 10. Что делать, когда сломалось

- `GET /api/health` — отвечает до лимитера, проверяет базу. На него стоит навести внешний монитор.
- `ALERT_WEBHOOK_URL` — сюда уходят: падение процесса, необработанная ошибка, любая 500-я, недоступная база, ошибка интерфейса в браузере. Повторы одного и того же — не чаще раза в 10 минут.
- Журнал действий в админке — кто и что менял, с деталями до и после.
- Логи сервера — обычный stdout.

## 12. Деплой

VPS: приложение работает как служба systemd под отдельным пользователем (`Restart=always`), перед ним Caddy (HTTPS, сжатие). Переменные `DB_PATH` и `BACKUPS_DIR` указывают на папку вне кода, поэтому обновление кода не трогает ни базу, ни её копии. Без них обе по умолчанию лежат в `data/` внутри проекта, и замена папки с кодом унесла бы базу: на новом сервере их нужно задать до первого запуска.

Выкладка — собранный `dist/` (и при необходимости `server/`) с копией предыдущей версии и перезапуском службы. Если менялись `package.json` или `package-lock.json`, перед перезапуском нужен `npm ci --omit=dev`: иначе сервер упадёт на новой зависимости.

Перенести локальные данные в прод: скачать копию, затем в панели «Восстановить из файла».

Обязательные переменные в проде: `JWT_SECRET`, `NODE_ENV=production`, `TRUST_PROXY=1`.

## 13. Чего здесь нет

Честный список — чтобы не искать несуществующее:

- нет учётных записей для преподавателей: страница часов открыта всем, кто знает фамилию;
- одна учётная запись администратора на всех, журнал не различает людей;
- деплой ручной, тесты в CI не гоняются;
- браузерных end-to-end тестов нет, покрыты API и модули;
- логика разбора шаблона и чётности написана дважды (сервер и браузер) и держится на парных тестах.
